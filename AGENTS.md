# AGENTS.md

ESP32 foosball-table firmware (PlatformIO/Arduino, C++) in `src/`, plus a no-build browser dashboard in `dashboard/` whose HTML is embedded into the firmware. Run commands from the repo root unless noted.

## Commands

- Build firmware: `pio run`
- Build + flash: `pio run -t upload`
- Dashboard preview: `pip install -r dashboard/requirements.txt`, then `cd dashboard && python3 server.py` → <http://localhost:8000/> (TV: `/tv`). `server.py` rebuilds the inline dashboard on startup; `--no-build` skips it.
- After editing `dashboard/index.html`, `dashboard/styles.css`, or `dashboard/app.js`, regenerate the embedded copy with `python3 dashboard/build_site.py` (writes `src/site.cpp` and `dashboard/dist/index.html`), then build/flash again.
- There is no test suite (`test/` contains only a README). Verify firmware changes with `pio run`; verify dashboard changes with `server.py`.

## Generated code and source of truth

- Never edit `src/site.cpp` or `dashboard/dist/index.html` by hand — both are generated by `dashboard/build_site.py`. `dashboard/dist/` is gitignored.
- `src/site.h` is hand-written and exposes `index_html` / `index_html_len`; `src/site.cpp` is a normal translation unit, not an include.
- Serve the page via the length overload in `src/webserver.cpp`: `request->send(200, "text/html", (const uint8_t *)index_html, index_html_len)`. The `const char*` overload copies the ~119 KB page to the heap and fails on the ESP32 (blank page).
- `src/config.h` is the pin/timing source of truth. `pinout.md` (top section) and the README's GPIO27/32 sensor note are stale: current pins are sensors 22/4, LEDs 16/17, stepper dir/enable/step 18/19/21, reset 23. README also references a removed `hardware/` directory.
- User-facing text (dashboard UI and README) is German; keep new UI strings German.

## Architecture

- `src/main.cpp` only wires modules in `setup()`/`loop()`. Modules: `sensors`, `leds`, `stepper`, `webserver`; cross-task state lives in `game_state`.
- Sensor flow: GPIO ISR → FreeRTOS queue → `sensorTask` → `reportGoal()`; `loop()` consumes the flag, updates score/LEDs and celebrates. After a goal both beam interrupts are disabled for 1 s, then beam states are re-synced.
- The 74HC14 inverts the beams: GPIO HIGH means beam blocked.
- WebSocket callbacks run in the async web-server task, while animations run in `loop()`. All `FastLED.show()` calls must go through `showLeds()` in `leds.cpp` (mutex); shared state must stay atomic in `game_state.cpp`. Do not add bare `FastLED.show()` or unsynchronised globals.
- Animations are non-blocking state machines advanced by `ledsTick()` from `loop()`; the web task only calls `requestLedUpdate()`. Never `delay()` for animation or ball-return timing — a blocked `loop()` leaves the strips stuck on one frame and can end in a watchdog reset. Always end an animation on `drawScore()` so the strips cannot stay on a transient frame.
- WebSocket protocol: text commands `t1_add`, `t1_sub`, `t2_add`, `t2_sub`, `reset`; broadcasts are `{"team1":N,"team2":N}`. It is implemented twice — `src/webserver.cpp` and the mock in `dashboard/server.py` — keep both in sync.

## Dashboard

- Sources are `dashboard/index.html`, `styles.css`, `app.js`; no npm/bundler. Tournament and player data persist client-side in IndexedDB (`FoosballTournamentsPro`, version 2); there is no server-side persistence.
- `dashboard/server.py` only mocks the ESP32 WebSocket for local preview; `/` and `/tv` serve the same generated page.
